# Specification: High-Fidelity Retro Rendering & Simulation Engine

## 1. Overview

This engine provides a high-performance, cross-platform pipeline designed to render vibrant, high-fidelity pixel art aesthetics without the memory or resolution constraints of vintage hardware. By decoupling simulation logic from the rendering loop, the architecture supports massive spatial scale—capable of handling everything from dense city simulation grids to sprawling, multi-layered platformer environments. The system delivers modern sub-pixel physics, dynamic lighting, and silky-smooth parallax scrolling while strictly enforcing the sharp, unblurred edges characteristic of classic 16-colour EGA pixel art.

## 2. Core Architecture Stack

The stack leverages a high-performance local-first approach, suitable for desktop and mobile distribution.

- **Simulation Core:** Rust compiled to WebAssembly (`wasm32-unknown-unknown`). Utilizes an Entity Component System (ECS) to manage thousands of active actors, spatial partitioning, and deterministic physics.
- **Rendering Engine:** Three.js acting as a thin wrapper over WebGL2 (with future-proofing for WebGPU). It strictly handles visual representation and matrix transformations, performing zero logical calculations.
- **Application Shell:** Tauri v2, providing a lightweight, cross-platform local execution environment that bypasses browser-based garbage collection bottlenecks and allows native file-system access for fast asset loading.
- **Memory Model:** Shared linear memory utilizing `Float32Array` buffers. This allows the Rust core and JavaScript renderer to read and write to the same memory space without expensive serialization or data copying.

## 3. Rendering Pipeline

The visual output bypasses traditional low-resolution render targets in favour of native display resolution, leveraging specific filtering and instancing techniques.

### 3.1 Camera System & Scaling

- **Implementation:** `THREE.OrthographicCamera`.
- **Behaviour:** Completely eliminates perspective distortion, keeping all sprites completely flat on the Z-axis.
- **Dynamic Viewport:** The perceived "chunkiness" of the pixel art is manipulated via the camera's zoom property. This allows seamless zooming from a macro-level map overview (e.g., viewing thousands of grid tiles) down to a micro-level character focus without swapping texture assets.
- **Aspect Ratio Maintenance:** On window resize, the camera's left/right/top/bottom frustum planes recalculate mathematically to prevent horizontal or vertical stretching of the pixel grid.

### 3.2 Asset Filtering & Texture Atlasing

- **High-Resolution Atlases:** Sprites and tiles (authored at 64x64 or higher) are packed into a single large texture atlas to minimize texture binding overhead on the GPU.
- **Strict Nearest-Neighbour:** Both `magFilter` and `minFilter` are hardcoded to `THREE.NearestFilter`. Mipmapping is explicitly disabled (`generateMipmaps = false`).
- **Edge Bleed Prevention:** To prevent floating-point inaccuracies from pulling colours from adjacent sprites in the atlas during sub-pixel scrolling, every sprite in the atlas includes a 1-pixel extruded border that duplicates the edge pixels.

### 3.3 Massive Instancing

- **Implementation:** `THREE.InstancedMesh` with a custom shader material that reads UV offsets.
- **Batching:** All static tiles and dynamic sprites utilizing the same texture atlas are batched into a single draw call.
- **Data Structure:** A customized instance buffer passes not only the standard 4x4 transformation matrix (position, rotation, scale) but also custom `vec2` attributes for UV offsets, telling the shader which specific sprite from the atlas to render for that instance.

## 4. Simulation & State Management (Rust/WASM)

Game logic, physics, and state mutations are fully isolated in the Rust WebAssembly core, executing at a fixed timestep to ensure deterministic behaviour.

### 4.1 Zero-Copy Memory Handoff (The Bridge)

- **Shared Buffer:** Rust allocates a contiguous block of memory to represent the visible entities on screen.
- **Data Layout:** Each entity occupies a fixed stride of floats in the buffer. For example, a 20-float stride per instance: 16 floats for the transformation matrix, and 4 floats for custom visual data (UV X, UV Y, tint colour, transparency).
- **Synchronization:** At the end of every simulation tick, Rust writes the updated values directly into this memory block. JavaScript reads this exact memory address into a `Float32Array` and binds it to the `InstancedMesh` via `.needsUpdate = true`. No JSON parsing or object instantiation occurs during the render loop.

### 4.2 Sub-Pixel Physics & Spatial Partitioning

- **Precision:** Velocity, acceleration, and AABB (Axis-Aligned Bounding Box) collisions are calculated at 64-bit floating-point precision. This ensures smooth acceleration curves and eliminates the "stuttering" commonly found in integer-based grid movement.
- **Data Structures:** The simulation utilizes a dynamic Quadtree or sparse grid to manage collision detection and frustum culling. The WASM core only pushes data to the shared memory buffer for entities currently intersecting the camera's view frustum, maintaining high performance even in maps containing millions of tiles.

## 5. Visual Enhancements (Hybrid Graphics)

Modern GPU capabilities enhance the retro aesthetic without compromising the crisp silhouette of the artwork.

### 5.1 Dynamic Lighting & Normal Mapping

- **Technique:** Flat 2D sprites are paired with hand-drawn or generated normal maps in a secondary texture atlas.
- **Shaders:** A custom GLSL shader calculates real-time point lights, casting dynamic shadows and highlights across the flat pixel art. This allows for environmental effects like glowing campfires, neon signs, or pulsing hazard lights that react to the geometry of the sprites.

### 5.2 Vector Overlays & UI

- **Decoupled UI:** User interface elements, complex data overlays, and typography are not rendered in WebGL. Instead, they are handled by a standard DOM layer (e.g., utilizing React or Svelte) positioned absolutely over the `<canvas>`.
- **Visual Clarity:** This hybrid approach allows menus, text, and floating-point particle effects to render at absolute native resolution without being forced into the blocky constraints of the pixel art environment.

## 6. Performance Targets

- **Frame Rate:** Locked 60 FPS (or native display refresh rate up to 144Hz) with strict frame pacing to prevent micro-stutters.
- **Entity Count:** Capable of maintaining target frame rates while rendering 50,000 to 100,000 active instanced tiles simultaneously on standard integrated graphics hardware.
- **Memory Footprint:** Zero garbage collection (GC) pauses during active gameplay. All WebAssembly memory buffers and Three.js object pools are pre-allocated during the loading phase.
- **Binary Size:** The compiled WASM payload is targeted to remain under 2MB, ensuring near-instantaneous initialization when launched via the Tauri shell.
