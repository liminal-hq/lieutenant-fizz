# SPEC: Retro Rendering & Simulation Engine (v0.2)

Revision of the original spec after the first two test games. Sections marked **Proven** are working (in the prototype and, where noted, in the Rust/WASM port); **Planned** items are not yet built.

## 1. Overview
A cross-platform pipeline for vibrant, high-fidelity EGA-style pixel art at native display resolution. Simulation runs separately from rendering: a deterministic fixed-step core writes into a shared buffer that a thin WebGL layer draws in one instanced call. The engine is game-agnostic; see `GAME_DESIGN.md` for the first title built on it.

## 2. Architecture
| Layer | Target | Prototype stand-in |
|---|---|---|
| Simulation core | Rust → WASM (`wasm32-unknown-unknown`), raw C-ABI exports; **done** (`crates/sim` plus `episodes/episode-1/game`) | `melting/engine.js` (plain JS, same data layout and tick boundary) |
| Renderer | Three.js r160+ over WebGL2 (WebGPU later) | Same: one `InstancedBufferGeometry` + `ShaderMaterial` |
| Shell | Tauri v2 | Browser tab |
| Audio | Undertone (`@liminal-hq/undertone`) | `melting/audio.js`: tries Undertone, falls back to a built-in mini-notation synth |
| UI | DOM overlay (React) | Design Component shell |
| Memory | Shared linear `Float32Array` | Pre-allocated `Float32Array`, 120,000 × 20 floats (9.6 MB) |

## 3. Rendering
### 3.1 Camera — Proven
- One `OrthographicCamera` per mode. Zoom spans a 3× close-up to a whole-level overview without swapping assets.
- On resize the frustum is recalculated from the viewport height in world tiles (13 for levels, 12 for the map, 14 for cinematics).
- The camera position snaps to the canvas-pixel grid each frame, so sprites never shimmer.
- The canvas is backed by device pixels, not a fixed pixel-ratio cap. **Soft** (the desktop default) backs it with `floor(css × min(dpr, 2, √(budget / cssArea)))` and shows the target tiles. **Sharp** (touch, `?touch`, `?pixels=sharp`) backs it with the device size divided by a whole `k`, and draws at a whole scale `s = max(2, floor(H / (16 × target)))` showing `H / (16 × s)` tiles, so the leftover height shows more of the level (no bars; Soft fallback below 11 tiles, when the size is not divisible by `k`, or when zoomed).
- **Fast** (`?pixels=fast`) is Sharp with one canvas pixel per sprite pixel. For the current screen's target it takes the whole scale `S` that Sharp would draw at, backs the canvas at `ceil(device / S)` and sizes its CSS box to `backing × S / dpr`, so the browser's pixelated upscale is exactly `S`× (the divisor `k` is `S`). The view is Sharp's on every screen (the tile count is `ceil(deviceH / S) / 16`, within one cropped sprite-pixel row of Sharp's `deviceH / (16 × S)`), and the backing is re-sized in the frame the screen's target changes (title, map, cinematic, level), on a resize, a rotation and a device-ratio change. About 9 to 100 times fewer pixels are shaded (25× at 844×390 at 3×). When the device size does not divide by `S` the canvas **overhangs** the right and bottom edges by under `S` device pixels and `#gl` (`overflow: hidden`) crops it, so the canvas **covers** the viewport rather than equalling it (Sharp and Soft still fill it exactly). Below 11 tiles Fast is Soft at half the ratio. The camera snaps to one canvas pixel, so under Fast scrolling and moving sprites step a whole sprite pixel (`S` device pixels) at a time and lighting falls off per sprite pixel. The CSS size is left unrounded (`backing × S / dpr` CSS pixels) so that, after the browser's pixel snapping, the box is exactly `backing × S` device pixels; captions are placed from the canvas's CSS box, since that box holds the camera's view. Pointer and touch input read no canvas geometry, so they are unchanged. `debugView` reports `fast`, `deviceScale` (device pixels per sprite pixel), `overscanW/H` and `cssCanvasW/H`.
- The renderer asks for no depth buffer (`depth: false`): the material neither tests nor writes depth.
- The **pixel budget** is 3840 × 2160 canvas pixels; larger desktop canvases are scaled down (Soft) or divided by `k` (Sharp). Width is not capped. The maths is in `packages/engine/src/view-scale.ts`.

### 3.2 Atlas — Proven
- Sprites are authored as palette-indexed grids (`sprites.js`, a small pixel DSL), then packed into one 2048² atlas at 4 texels per logical pixel.
- Filtering is `NearestFilter` for min and mag, with mipmaps off.
- Every sprite has a 1-pixel extruded border; tile sprites clamp edge height for seamless normals.
- A second atlas with the same layout holds the generated normal maps (§5.1).

### 3.3 Instancing — Proven
- Everything is drawn in one draw call per frame: parallax, tiles, items, enemies, shots, effects and player.
- Instance stride is 20 floats: `iM0–iM3` hold the 4×4 matrix, with UV width and height packed into the spare w components of the first two rows, and `iData` holds (u, v, tint RGB packed as 24-bit, alpha + 2·emissive).
- Draw order is buffer order (painter's algorithm, no depth test).

## 4. Simulation
### 4.1 Bridge — Proven
- The buffer is allocated once at boot and written front-to-back each frame.
- Only `[0, n × 20)` is uploaded (`addUpdateRange`), and `instanceCount = n`.
- There is no JSON or object creation in the render loop. A light pool, uniforms and vectors are pre-allocated.

### 4.2 Physics — Proven
- 60 Hz fixed step with an accumulator (max 0.25 s catch-up) and render interpolation between the previous and current state.
- AABB versus tile grid, with separate X then Y resolution.
- Tile types: solid, one-way platform, 45° and 22.5° slopes (two tiles per 22.5° rise), spike, chocolate (liquid hazard), keyed doors, switchable tiles on up to 32 independent switch channels, conveyors (left and right, 3 tiles/s), ladders (a ladder top is a one-way ladder tile).
- 0.55-tile step-up when grounded; slope snapping keeps walking downhill glued to the surface.
- Moving platforms carry riders by their per-tick delta, and can rest for a set time at each end (lifts that wait at every floor). A body standing on a conveyor is carried along it as a step of its own, on top of its own velocity, so a belt that pushes it into a wall never cancels its own motion and it can still walk away.
- **Done:** the Rust port with f64 state (`crates/sim` and `episodes/episode-1/game`).
- **Planned:** sparse grid or quadtree for entity–entity tests (currently O(n) per level).

### 4.3 Culling — Proven
- Tiles iterate only the visible rectangle; entities, items and platforms are skipped when outside the view plus a margin.
- The stress test adds a 400 × 125 back wall (50,000 tiles). Culling on writes ~1–2k instances; culling off writes ~54k.

### 4.4 Save state — Proven
- Autosave (meta progress) on every overworld visit.
- **Storage adapter:** saves, options and touch settings (every `lf-*` key) go through the synchronous `KeyValueStorage` interface in `packages/engine/src/storage.ts` (`getItem`, `setItem`, `removeItem`, `keys`), never `window.localStorage` directly. `createStorage()` runs once at boot, before the game is built, and takes the first backend that opens from an injected list: the Tauri store file (`tauri-storage.ts`, only inside the app, detected by `window.__TAURI_INTERNALS__`), then the browser's `localStorage`, then a store in memory. The web build keeps using `localStorage`. The Tauri backend reads every key from `lf-data.json` into memory before the game starts so reads stay synchronous, writes through to the file in the background (gathered into one batch after 250 ms) and flushes when the page is hidden or goes away. A batch reaches the file through the app's own `write_store` command, which sets, removes and saves in one native call, so a page that Android suspends right after the flush starts has still handed over every write. If the file fails the game carries on from memory and logs the failure once. A memory store is handed to the game as "no durable storage", so saving reports a failure just as it does when the browser blocks `localStorage`. `debugState.storage` reports `local`, `tauri` or `memory`. `sessionStorage` is not used.
- Saves are progress-level in the Rust port: lives, score, ammo, cleared levels, map position and time played, in `localStorage`. The prototype serialised the full simulation (tile map, entities, items, shots, keys, platforms); restoring that in the port needs a serialisable world in Rust and is **Planned**.
- **Slots:** the autosave keeps the original key (`lf-ep1-save-v1`) and is read-only in the save screen; four manual slots live under `lf-ep1-slot-1` to `lf-ep1-slot-4`. Each stores `{ v, at, progress }`. F5 saves to the most recently used manual slot (Slot 1 if none), F9 and Continue load the newest save of any slot, and the pause menu's Save game and Load game open the slot screen.
- **Versions:** the save version is 3, which adds `played` (seconds). Version 1 and 2 saves still load: version 1 loses its map position (it belongs to the old map) and both start with no time played.
- **Options:** music and effects volume (8 blocks each), the sound style (`audio`: 0 Auto, 1 Classic, 2 Enhanced), captions, controls layout, text size, motion and the Sound lab switch (`lab`, a boolean, off by default; see "Sound lab") are saved together under `lf-ep1-options-v1` (still `v: 1`; the `audio` field is new, an older save loads with Auto, and `lab` is new, an older save loads with it off, and missing or invalid fields fall back to their defaults). The volumes and the style are set on the Sound screen, opened from the first Options row; see "Classic and Enhanced".
- **Slot thumbnails** are not stored. The sim exports the overworld as one byte per tile (`thumb_ptr`, `thumb_w`, `thumb_h`: grass with its area, river, or a level node) and `area_of`; the shell paints the mini map at 1 pixel per tile from those and the saved cleared levels and map position.

## 5. Visuals
### 5.1 Lighting — Proven
- Normal maps are generated from sprite luminance height (Sobel-style, strength 2.2).
- Up to 16 point lights per frame are chosen nearest-first from a pool of 256, with Lambert diffuse and quadratic falloff.
- Light sources: player lantern, crystals (flicker), hazard rows (pulse), pickups (soft glow by type), shots, sentries, spore puffs, terminal, boss weak point.
- Two ambient profiles per biome:
  - **Day** (default): bright ambient, lights at 55–60%.
  - **Night**: low ambient, full-strength lights, and a gradient sky drawn behind a transparent canvas.
- Emissive flag (alpha + 2) bypasses lighting for UI-like sprites (crystals, exit, items, effects).
- Optional posterise step: lighting is quantised to quarter steps.
- **Planned:** cast shadows (2D shadow-volume or SDF pass).

### 5.2 DOM overlay — Proven
- HUD, menus, dialogue, cinematic text and world-anchored "sound captions" render in the DOM at native resolution.
- The engine emits events (`hud`, `stats`, `toast`, `levelComplete`, `dialogue`, …); the shell never reads simulation state directly.
- **Typography:** every overlay surface is set in the Fizz pixel font family (see `docs/FONT.md`). Text is only crisp at whole-pixel sizes, so `font-size` is always `11px × n` for a whole number `n` from 2 to 6, and each glyph pixel is exactly `n` CSS pixels. Pixel text never uses `clamp()`, viewport units or fractional sizes, and spacing around it is written as multiples of `n` pixels.
- **Scale selection:** the shell picks the item scale from the window height (2 under 480 px tall, 3 up to 900 px, 4 above; Options › Text size › Large adds one) with `pixelScale` in `packages/engine/src/font/scale.ts`, and writes the derived scales to CSS custom properties (`--lf-n`, `--lf-n-small`, `--lf-n-head`, `--lf-n-hint`, `--lf-n-logo`) on resize. Small text is one step below the items and never under 2; headings are one step above and never over 6; hints and notes are always 2. A component sets `--n` to the scale it uses and everything under it takes its font size, line height and spacing from that.
- **Rendering:** overlay text sets `-webkit-font-smoothing: none`, `font-smooth: never` and `text-rendering: optimizeSpeed`, and the faces load with `font-display: block`. Long text wraps at word boundaries.
- **Title attract mode:** the title screen runs the sim in `Mode::Attract` and pans a deterministic camera across Crater Fields, then Crystal Caves, then Mildred's Citadel, and round again. `load_attract(idx, still)` loads one level; the camera position is a function of the tick count alone (2.2 tiles/s back and forth across at most 46 tiles, from just inside the left wall), and its bottom edge sits on row 0, so it never shows below the bottom tile row. `State.ATTRACT_T`, `ATTRACT_PERIOD` and `ATTRACT_IDX` let the shell fade a black layer over the last and first half second and call `load_attract` for the next level; with reduced motion `still` holds the camera and the loop does not advance. A small "Attract · {level}" label sits bottom-right from 560 px wide.
- **Ben on the title** is presentational (`titleBen.ts`): he stands at the end of the wordmark with a one-pixel bob, leans on it now and then, hops up and pogoes across the top of it on a 14 second loop, faces the menu for 1.6 s when the selection moves, and does the shoot pose as a wave for 0.9 s when an item is picked (the choice takes effect 0.65 s later). He only stands under reduced motion and is hidden when the window is under 420 px tall.
- **Menus:** left-aligned and unboxed over a scrim. The selected row is a stepped-corner plate (4 px notches) in `#ffaa40` with dark ink, cycling through four warm steps; the bullet is the soda sprite, drawn once from the sprite grid and shown pixelated in a fixed gutter so rows never shift. Both stop under `prefers-reduced-motion`. Meter rows show 8 blocks, and choice rows show `◄ value ►` while selected.

### 5.3 Credits and stinger — Done (shell logic and Episode 1 credits); Episode 3 stinger content Planned
- **Flow:** ending panels, then the credits, then (only if the episode has one) the stinger, then the score card. Both scenes are skippable with Esc or gamepad Start. Screen state lives in the TypeScript shell; the Rust simulation is not involved and stays deterministic.
- **Content:** an episode supplies an `EpisodeConfig` (`packages/engine/src/episode.ts`) with `credits` (title card, sections of role and name, a closing heading, a closing line and a final return line) and `stinger` (`null` for no stinger). Episode 1's credits are data in `episodes/episode-1/src/credits.ts`; its config sets `stinger: null`.
- **Credits roll:** `CreditsRoll` (`packages/engine/src/credits.ts`) is a pure state machine driven by frame times. The text scrolls up from below the viewport over the Afterglow wash and faint stars at the larger of 40 px/s and 10% of the viewport height per second, and holds with the closing card centred. Jump (or Enter, or a click) speeds up to four times and slows back down; once held it continues. Esc or Start skips. Frame steps are capped at 50 ms. Music is the ending track.
- **Reduced motion:** with `prefers-reduced-motion: reduce` the roll does not scroll; it shows one page at a time (title card, each section, the close), and Jump turns the page, then continues.
- **Story beats:** `BeatCursor` (`packages/engine/src/story-beats.ts`) is the pure state behind the letterboxed story screens (an episode's opening cinematic and ending). A scene is a place and its `beats`, the pieces of text read one at a time, and the scene keeps its art across them. The cursor holds the scene, the beat and how much of the beat is typed (83 characters a second, driven by frame times). `press()` completes a beat that is still typing and returns `complete`; otherwise it moves to the next beat (`beat`), then the first beat of the next scene (`scene`), and on the last beat of the last scene returns `end` and stays put for the host to leave the sequence. `view()` gives the text split into the typed and the not-yet-typed part (the shell keeps both in the layout so the line never reflows), the place, `done`, `sceneEnd`, `last`, the dots (one filled for each scene reached, an open one for each to come, so progress is by scene, not by beat) and the announcement. With reduced motion every beat is whole as soon as it starts, so one press advances. The shell marks the typed text `aria-hidden` and gives a screen reader one `aria-live="polite"` line that receives the whole beat once, when it starts, with the place added only when the scene changes. The shell does the rest: the art per scene, Skip and the buttons. Dialogue, the cards, the credits and the stinger do not use it.
- **Stinger:** `StingerScene` (`packages/engine/src/stinger.ts`) is a pure timing state machine: silence until 1.2 s, then the low sting (the `stinger` effect, with the sound caption `♪ low sting`) and a slit of light, at 2.6 s the slit opens into a doorway with the figure, at 4.6 s the name and line type out at 83 characters per second. Jump is ignored until the line appears, then completes the typing, then continues. Esc or Start skips at any time. Music is off from the credits' end until the score card. The Mortimer figure is the `billyAlt` sprite.
- **Preview:** Episode 1 does not show the stinger (it belongs to Episode 3). Add `?previewStinger` to the page URL to see the Mortimer stinger after the Episode 1 credits.
- **Planned:** Episode 3's own stinger content and a gamepad-only pass on real hardware.

## 6. Audio (new)
- **Target:** Undertone 0.2 patterns (`@liminal-hq/undertone` ^0.2.0). Each sound effect is a `stack` of voices (`note|sound`, ADSR, `lpf/hpf`, `slide`, `nudge`); music is a looped `stack` of mini-notation parts at a fixed BPM, with `room` and `delay` sends.
- **Fallback:** the built-in synth parses the same subset of mini-notation (`[ ]`, `< >`, `,`, `*n`, `~`) and schedules voices 300 ms ahead.
- The audio context unlocks on the first click or key press. Audio is a single global instance, disposed on unmount (prevents doubled loops on hot reload).
- Caption events double as sound-effect triggers, so audio and captions always agree.
- **Classic and Enhanced:** `GameAudio.mode` is `classic` or `enhanced`. Enhanced is the game's default (`AUDIO_DEFAULT` in `sound-field.ts`, applied through `resolveAudioMode`), and the mode in effect is chosen by, in order, `?audio=classic` or `?audio=enhanced` (`GameOptions.audio`), the player's saved Style on the Options > Sound screen (Classic or Enhanced; Auto means none) and `AUDIO_DEFAULT`. The link wins for the whole session and never writes the saved choice; while it is set the Style row shows the forced mode with "(link)" and cannot be stepped. Stepping Style saves an explicit choice (Auto shows what it resolves to); Reset on the Sound screen (two taps within three seconds) puts Style back on Auto and Music and Effects at full, and changes no other option. Each step on Style or Effects plays a short preview 250 ms after the last step: Style plays a boing at pan -0.5 then a plink at +0.5 after 160 ms (Classic plays both centred, so one step is the comparison) and Effects play a crunch at the new level; Music changes live on the music bus in Enhanced and restarts the loop in Classic. The Sound screen's music mix is always open (`mixFor` with `sound`), even when it is opened from Pause. `GameAudio` itself still starts in Classic, so the engine changes nothing until a game asks for a mode. `__lf.debugAudio('classic' | 'enhanced')` under `?debug` switches live, and its report says whether the mode was forced by `?audio=` or is the default. Classic is the sound as it has always been: effects play with `play({ ctx })` and music loops with `loop({ ctx, bpm })` on the real context, straight to `ctx.destination`, and no panner or other node is ever created for them. The mode only affects sounds that start after it changes, and switching back to Classic restores that path exactly.
- **Sound field (Enhanced, first stage):** `packages/engine/src/sound-field.ts` holds the pure maths. `placeSound(x, y, camera, half)` measures the offset from the camera in half-screens (1 is the edge of the view), sets the pan to `FIELD.width` (0.6) times the horizontal offset clamped to ±1, and the loudness to 1 out to `FIELD.near` (one half-screen on the further axis), falling by `FIELD.slope` (0.5) per half-screen beyond and never below `FIELD.floor` (0.4), so a far sound is quieter but never lost. Sounds with no position (menu and click sounds, cinematic captions) sit at the centre. The sim already reports a position for every sound (the `CAPTION` event carries the world `x` and `y`), so nothing in the simulation changed.
- **Routing:** each Enhanced effect gets its own emitter (a gain, then a stereo panner, then the master chain's `sfxBus`) and Undertone is given a routed context (`routedContext` in `sound-graph.ts`: the real context with `destination` replaced by the emitter). Undertone's voices connect to `ctx.destination`, so they end up in the emitter, and no change to Undertone is needed. The routed context is a new object, so Undertone's per-context reverb and delay buses are separate from the real context's (effects have none today). The built-in synth is given the emitter as its output.
- **Loudness at the centre:** a mono voice through a stereo panner at pan 0 is 3 dB quieter than the same voice sent straight to a stereo output (0.707 on each side against 1), so the emitter's gain includes `PANNED_MAKEUP` (√2). A centred Enhanced sound is as loud as Classic; at pan 0.6 the sides are 0.44 and 1.34 with the same total power.
- **Music stereo field (Enhanced):** every music part has a `role` (`PartRole`: `bass`, `kick`, `snare`, `pad`, `drone`, `lead`, `counter`, `bell`, `hats`, `perc`, `arp`), and `PART_PAN` in `sound-field.ts` places each role: bass, kick, snare, pad and drone stay centred; lead -0.15, counter 0.2, bell 0.3, hats 0.25, perc -0.3; the arpeggio ping-pongs between -0.3 and 0.3 on every eighth of the cycle (`partPanAt(role, cyclePos)`). The helpers (`kick`, `hats`, `snare`, `pad`, `bell`) set their roles and the other parts are labelled by hand in `patterns.ts` by what they play. In Enhanced the music loops through a routed context (`createMusicBus` in `sound-graph.ts`) into a music bus that feeds the master chain (below; straight to the destination if the chain cannot be built); Undertone's room and echo buses for that context feed the same bus. A panned part gets Undertone's `.pan()` (`undertonePan(role)`, which for the arpeggio is the pattern `[-0.3 0.3]*4`) and the `PANNED_MAKEUP` gain on its voices; a centred part gets neither, so it is exactly as loud as in Classic. The built-in synth does the same with its own panner, so both back ends agree, and its echo line for the music bus feeds the bus. Switching the mode mid-track restarts the loop on the other route.
- **Mastering chain (Enhanced):** `packages/engine/src/master.ts` builds the chain the first time Enhanced plays anything and takes it down about two seconds after the switch back to Classic (a quick switch back keeps it), so Classic never has any of it. Sound effects go into the `sfxBus` and music into the `musicBus`; both are summed and run through a 22 Hz high-pass, a low shelf (150 Hz), a presence band (3.2 kHz, Q 1) and a high shelf (9 kHz), all three at 0 dB by default so they colour nothing until tuned, a bus compressor (-8 dB, knee 6, ratio 1.8, attack 6 ms, release 180 ms), a limiter (-1 dB, knee 0, ratio 20, attack 1 ms, release 80 ms), an output trim and the destination. A small room runs beside it: a send of 0.10 of the sound effects and 0.06 of the music (each times `ROOM_SEND_SCALE`, see Rooms) goes through a 300 Hz high-pass, a 5 kHz low-pass, a 12 ms predelay and a convolver, and rejoin the chain at the compressor. The impulse response (`roomImpulse(sampleRate, seconds, seed)`) is seeded noise with a 3 ms fade-in decaying to -60 dB over 0.8 s (0.6 s on a coarse pointer), with a different seed per channel so the tails differ left to right; it is the same on every device. The dry signal gets no Haas delay, mid/side processing or decorrelation, so a mono fold-down sounds like the stereo mix. Every starting value lives in the mutable `MASTER` constant. If the context cannot build the chain, Enhanced plays unmastered, as it did before the chain existed.
- **Transparent by default (measured):** the first mastering values (shelves +1.5 and +1 dB, a 3.2 kHz dip of 1 dB, a 2.5:1 compressor at -16 dB, a limiter at -2 dB, trim 0.55) were found, by rendering all 28 effects and 11 music tracks through the real chain in Chromium against the same material played straight, to leave Enhanced quieter than Classic (effects -1.1 dB on average, up to -3.1 dB; music -1.3 dB, up to -2.9 dB) and to take the 2 to 8 kHz band 1.5 to 2 dB under the rest of the music on average (up to 4.2 dB on a track) and up to 5 dB on loud effects such as `bonk`, `thoom` and `clunk`: the compressor pulls the whole signal down when the bass peaks, the dip adds to it, and a trim that cancels the make-up of quiet material is too low for loud material. The defaults are now flat: all three EQ gains 0 dB, a compressor that only acts above -8 dB at 1.8:1, a limiter at -1 dB and a trim of 0.8 (`trimToCancelMakeup()` gives 0.80). A white-noise render through the sound-effect path, the music path and the bare master is within 0.03 dB of a straight pass from 1 to 20 kHz at 24, 32, 44.1 and 48 kHz; on the same 39 sounds the output level is within 0.1 dB of Classic on average (extremes -0.4 and +0.7 dB), and every band from 1 to 16 kHz stays within 1.7 dB of the overall change on any one sound (0.4 dB on average). The shelves and the presence band are still there to tune by ear; they simply start at 0. **Loudness trap and the trim:** a browser `DynamicsCompressorNode` adds make-up gain of its own, `(1 / curve(1.0)) ^ 0.6`, whatever the level of the signal. With the defaults the compressor adds about 1.4 dB and the limiter about 0.6 dB (`makeupDb`, `chainMakeupDb`: 1.93 dB), which the 0.8 trim cancels. The make-up is the same at every level but the compression it follows is not, so the lower the threshold and the higher the ratio, the more a loud passage comes out under a quiet one; the earlier -16 dB, 2.5:1 compressor added 5.1 dB and its trim could only be right for quiet material. A start for matching by ear, not the end of it. Sounds rendered at time zero of an `OfflineAudioContext` read 6 to 17 dB low while the compressor warms up, so measure with the sound starting half a second in.
- **Tuning live:** under `?debug`, `__lf.debugAudioTune(tune)` changes any value of `MASTER`, `FIELD` and `PART_PAN` while the game runs (`applyAudioTune(tune, { mix, rooms })` in `audio-tune.ts`, which takes the episode's mix states and room table to change). The shape is `{ master?, field?, partPan?, mix?, rooms? }` (`mix` is described under Mix stage and `rooms` under Rooms), each holding only the values to change: `master` mirrors `MASTER` (`trim`, `comp.ratio`, `limiter.threshold`, `lowShelf.gain`, `presence.freq`, `reverb.sfxSend`, `reverb.seconds` and so on), `field` mirrors `FIELD` (`width`, `near`, `slope`, `floor`) and `partPan` maps a role to a pan (a number, or a `[left, right]` pair for `arp`). Master values glide with `setTargetAtTime` so there is no click, a new impulse-response length rebuilds the room, and a new `partPan` restarts the music because the pans are part of how the voices are built. Examples: `__lf.debugAudioTune({ master: { trim: 0.6 } })`, `__lf.debugAudioTune({ master: { comp: { ratio: 3, threshold: -20 }, reverb: { sfxSend: 0.05 } } })`, `__lf.debugAudioTune({ field: { width: 0.4 }, partPan: { bell: 0.2, arp: [-0.4, 0.4] } })`. It returns `{ applied, ignored }`: unknown keys, non-numbers and pans outside -1 to 1 are skipped and listed, not thrown. Changes last until the page reloads; copy the values you like into `MASTER`, `FIELD` or `PART_PAN`. `__lf.debugAudio()` also reports `masterBuilt`.
- **Mix stage (Enhanced):** the music bus runs `bus -> level -> low-pass -> mix gain -> master music bus` (`createMusicBus` in `sound-graph.ts`). `level` carries the music volume, so in Enhanced a volume change glides (`setTargetAtTime`, 20 ms) and the loop is not restarted, because the patterns are built at full level; Classic still bakes the volume into the patterns and restarts. The low-pass (Q 0, flat at the cutoff) and the mix gain take a `MixShape` (`{ lpf, gain }`, 20000 Hz is open) from `GameAudio.setMix`; an open cutoff is set on the filter as the context's Nyquist frequency (`lpfHz` in `sound-graph.ts`), because a biquad low-pass at 20 kHz is not open on a 44.1 or 48 kHz context (measured: up to +0.95 dB from 12 to 18 kHz, -1.0 to -1.2 dB at 20 kHz and -5 dB at 22 kHz from its Q of 0 dB), while one at exactly Nyquist is the identity, which closes over 0.18 s and opens over 0.35 s (`MIX_RAMP` in `mix.ts`). The cutoff ramps exponentially and the gain linearly. A new change starts from where the last has got to: the last ramps are kept in JavaScript and read with `valueAt(ramp, t)`, then `cancelScheduledValues(now)`, `setValueAtTime(current, now)` and a ramp are scheduled, so nothing relies on `cancelAndHoldAtTime` (missing in Firefox) or on reading `param.value`. Pausing at t = 10.00 puts the cutoff at 7114 Hz at 10.06, 2530 Hz at 10.12 and 900 Hz at 10.18, with the gain 1 to 0.7 (-3.1 dB). In Classic, or before the bus exists, `setMix` only stores the shape; it is applied without a ramp when the bus is built, and `setMode('enhanced')` applies the stored shape again. While the page is hidden (`setActive(false)`) the context is suspended and its clock frozen, so a change is made at once, not as a ramp, and the pause menu is already muffled when the page returns. Episode 1 (`episodes/episode-1/src/audio/mix.ts`) names the shapes: `mixFor(screen, sub)` gives Pause and the Options, Saves and Controls screens opened from it 900 Hz at 0.7 (1400 Hz on a coarse pointer, `pauseCoarse`, since a phone speaker has little left below that), the level-cleared and game-over cards 2200 Hz at 0.8, dialogue 0.7 (-3 dB) and the cinematic and ending panels 0.85 (-1.4 dB) with the cutoff open, and everything else (title and its sub-screens, play, the map, credits) open. `syncUi` sends the shape on every screen change. Sound-effect ducks are a later stage. `__lf.debugAudio().mix` reports `{ lpf, gain, applied }` (the shape last asked for, and whether the bus carries it), and `__lf.debugAudioTune({ mix: { pause: { lpf: 700, gain: 0.6 } } })` changes a named shape (`open`, `pause`, `pauseCoarse`, `card`, `dialogue`, `cine`; `lpf` 20 to 20000 Hz, `gain` 0 to 2) and re-applies it to the screen showing.
- **Rooms (Enhanced):** each kind of place has its own reverb, always on in Enhanced (there is no Rooms row; Classic is the dry choice and builds nothing). `RoomProfile` (`master.ts`) holds a room's length (and a shorter one for a coarse pointer), the sfx and music sends, the send's high-pass and low-pass, the predelay, `damping` and an optional `ring`, and a seed. `roomImpulse(sampleRate, seconds, seed, shape?)` takes a `RoomShape`: `damping` runs a one-pole low-pass over the tail whose coefficient goes from 1 at the start to `1 - 0.9 * damping` at the end, so the tail darkens as it dies; `ring` adds a comb resonance, `y[i] += amount * y[i - round(sampleRate / hz)]`, for a hall or tube that rings. With no shape, damping 0 and no ring the samples are exactly the 8b.3 room (a test checks hashes taken from that code). `roomSeeds(seed)` gives the left and right seeds, `[seed * 2 + 1, seed * 2 + 2]`, with seed 0 keeping the original pair. `Master.setRoom(profile, fade = 0.8)` builds the new impulse response (cached by key) into the idle one of two convolver slots, each with its own predelay and crossfade gain, and moves between the slots with an equal-power `setValueCurveAtTime` of 16 points (cos out, sin in, so the powers add to 1 and the uncorrelated tails keep their level). The sends and the send filters glide with `setTargetAtTime` (time constant fade / 3), the old slot's buffer is released after the fade plus the length of its tail, and a room asked for during a crossfade waits for it and a later request replaces an earlier one. A swapped buffer would click, which is why there are two slots. `GameAudio.setRoom` only stores the room in Classic or before the chain exists; the chain is built in it, and switching back to Enhanced applies it. The episode's table is `ROOMS` in `episodes/episode-1/src/audio/rooms.ts` (neutral, map, outdoor, cave, shaft, citadel, tower, theatre, foundry), each level names its room in `LEVELS[].room`, and `roomFor(screen, mode, levelId)` picks one: the title, cinematics, ending and credits use `neutral` (equal to `MASTER.reverb`, the 8b.3 room), the map has its own and a level, with its pause, card, dialogue and stinger screens, keeps its level's room. The game moves rooms from `syncUi`. On a coarse pointer the sends are 0.8 times lower and the shorter length is used (measured, a coarse cave is about 3.7 dB under the desktop one). **How much room a send gives:** a `ConvolverNode` normalises its response, which leaves a send of 1 about 13 dB under the dry sound, so the send nodes are set to the room's `sfxSend` or `musicSend` times `ROOM_SEND_SCALE` (8, +18 dB). Measured with a click through the real chain, the energy of the reverb against that of the dry sound is `20 log10(send * 8) + C`, where C is the room's constant (-13.3 dB for the 1.8 s cave, -18.0 for the neutral room; damping does not change it, length does a little); at the old scale the cave at 0.22 was 26 dB under the dry sound and its tail past 0.4 s 38 dB under, which cannot be heard, and the 0.4 a listener tried (+5.2 dB, as measured) was still 21 dB under. The table now aims at the reverb being about 4 dB under the dry effects in the cave, 6 in the shaft, 8 to 10 in the citadel, theatre, foundry and tower, 20 in the neutral room, 24 on the map and 31 outdoors (music a further 7 to 9 dB lower), and the lab's send sliders run 0 to 1. A send of 1 is therefore a very wet room (the reverb about 5 dB over the dry sound). Retuning a room live does reach the chain: the sends and filters retarget whenever `setRoom` is called, even for the same room, and the response is rebuilt whenever the length (the coarse length on a phone), `damping` or `ring` changes. `__lf.debugAudio().room` names the current room. Retune one live with `__lf.debugAudioTune({ rooms: { cave: { sfxSend: 0.15, seconds: 2.2 } } })` (any number of a room, including `ring.hz` and `ring.amount` for rooms that have a ring; the room is rebuilt and crossfaded if its response changed), or `{ rooms: { citadel: { damping: 0.2 } } }`; `master.reverb` only sets the room the chain is built in, which the neutral room then replaces, so tune `rooms.neutral` for the title. The Web Audio `ConvolverNode` normalises its response by default, so a longer room is not louder by length, only by its send; the sends and the trim are still the place to match loudness by ear.
- **Sound lab (`?debug` or the Sound lab option):** `__lf.debugLab(open)`, called by `main.ts` for every `?debug` page (and opened by `?debug&lab`, or `?debug&lab=haptics` for the haptics lab), adds a Lab button and a full-window overlay `#lab` in `#ui`. The one Lab button belongs to `ui/lab-shell.ts` and is shared with the haptics lab (see 6.1): the shell opens whichever lab was used last, each lab's header has a Sound | Haptics switch while both can be reached, and only the open lab's `#lab` root is in the page. The same lab is available without `?debug` when Options > Sound > Sound lab is On (`lab` in `lf-ep1-options-v1`, default off); `?debug` shows it whatever the option says. `Game.syncLab` mounts or removes it whenever the options change, with no reload: the lab modules (`ui/sound-lab.ts`, `audio/lab.ts`) are imported on demand, so with the option off and no `?debug` nothing of the lab is fetched, built or in the page, and turning it off closes the lab, removes its button and overlay and puts back anything it tuned or held. Reset on the Sound screen turns the option off. It lists every name in the episode's `SFX` table (a button plays it, placed by a Pan slider, -1 to 1, and a Distance slider, 0 to 4 half-screens, whose loudness is `placeSound`'s fall-off from the live `FIELD`; the pan is as set, so above `FIELD.width` it is wider than the game ever places a sound) and every track in `MUSIC` (tap to play, tap again to stop, "Follow the game" gives the music back). The header has a live Classic or Enhanced toggle (`setMode`), 'Copy as JSON' and 'Reset to defaults'. A room picker (every key of `ROOMS`, or 'Follow level') and a mix picker (every key of `MIX`, or 'Follow screen') hold a room or mix state in place of the game's choice (`labRoom` and `labMix` in `game.ts`, read by `updateRoom` and `syncMix`) until 'Follow' is chosen. Sliders cover the master chain (trim, compressor threshold, ratio and knee, limiter threshold, the three EQ gains), the effect field (width, near, slope, floor), the music pans (including both sides of the arpeggio), the picked room (sends, length, damping, send low-pass) and the picked mix state (cutoff on a log scale, gain). Each moves the live tables through `debugAudioTune`; the pans and the room sliders apply on release because they restart the music or rebuild the room. 'Copy as JSON' copies only what differs from the values captured when the page loaded (`LAB_DEFAULTS`), in the shape `__lf.debugAudioTune` takes, so it can be pasted back to the developer or replayed; 'Reset to defaults' applies the reverse diff. The pure parts (item lists, slider ranges, steps, units, the diff, `auditionAt`) are in `episodes/episode-1/src/audio/lab.ts` with unit tests; the DOM is `ui/sound-lab.ts`. Auditioning calls the audio directly and never changes saved options or game state, but a held track keeps the game's own music choice from taking over, and music or sound switched off in Options still silences the lab (its status line says so). In Classic the lab builds nothing extra: effects play centred and the sliders are kept until Enhanced returns. The lab does not prove a setting is good: it makes a setting easy to hear. Layout is checked by `e2e/lab.spec.ts` (type sizes and 48 px targets at 844x390, no audio); how it sounds, and the lab on a real phone, are by ear.
- **Not yet built:** Night mode and Mono rows (8c.5), surround, and an automated loudness probe (the measurement above was a one-off script, not a test).
- **What the tests prove:** unit tests with a recording fake `AudioContext` check the pan and falloff maths, the role table and that Undertone's events carry the pan `partPanAt` gives at each onset, the graph edges, the exact `play`/`loop` arguments, that each call's voices connect to that call's emitter, and that Classic never builds a panner. They check the chain order and edges, that it is built lazily and detached after Classic, the trim and make-up numbers and the impulse response (deterministic, the right decay, left and right correlated under 0.2). The mix tests check the ramp maths against the worked examples, the exact automation calls, that a change in mid-glide starts from the current value, that a mix asked for early or in Classic is applied when it should be, that the volume moves without a restart, and that Classic builds no extra node. The room tests check the shaped impulse responses (the 8b.3 room unchanged when no shape is given), the two-slot crossfade automation, the room table and which room each screen and level gets. They cannot show how the muffle and the ducking sound, whether a retarget clicks (an offline render would, locally), or how a 900 to 1400 Hz low-pass comes out of a phone speaker. They cannot show that Enhanced sounds better, that its loudness matches Classic on real music, or what the EQ and room do to a particular track; that takes listening on headphones and on a phone speaker (which is often mono in landscape, so the field mostly shows on headphones).

### 6.1 Haptics — Core, rumble and the settings screen built
- `haptic-pattern.ts`: portable patterns (transient taps and continuous hums with intensity and sharpness), cue and table types, and `compileVibrate`, which turns a pattern into the on/off array `navigator.vibrate` takes (`VIBRATE_COMPILE` holds the constants).
- `haptic-backends.ts`: `HapticBackend` (`caps`, `play`, `stop`, `dispose`), `noneBackend`, `vibrateBackend(navigator)` (detects by type, treats a `false` return as unavailable, waits for `navigator.userActivation.hasBeenActive`), `gamepadBackend(getPad)` (dual-rumble through `vibrationActuator`; a pattern is up to eight steady segments, each fired by a timer, cancelled on a new play or `stop()`, which calls `reset()`; rejections are swallowed) and a recording `fakeBackend` for tests. `compileRumble` turns a pattern into those segments (`RUMBLE_COMPILE`). Browser globals are injected, so tests never touch `navigator`.
- `haptics.ts`: `GameHaptics(table, clock)` beside `GameAudio`. The game raises cues with `cue(id, scale, onScreen)`, `caption(text, onScreen)` and `ui(kind)`, and calls `flush()` once a frame; at most one cue plays, chosen by priority (then the longer pattern). There are two targets, `device` (the vibrator) and `controller`; `setBackends({ device, controller })`, `setRoute(route)` and `setScale(device, controller)` configure them, `routeFor(inputDevice)` maps a gamepad to the controller and touch or keyboard to the device, and the `ui` lane always stays on the device. Each target has its own running pattern and queue and gets at most one call a frame. Policies are `interrupt`, `drop-if-busy`, `queue` (waits up to 250 ms for the running pattern) and `{ coalesce: ms }` (folds repeats, +15% each up to three). A lower priority never cuts off a higher one still running, cooldowns apply per cue, and the phone's vibrator has a 400 ms-per-second budget (priority 4 exempt). Cues marked `world` are felt only when on screen (`onScreen(x, y, cam, halfW, halfH)`), and `setCalm(true)` shortens and softens cues marked `calm`. `audition(pattern, target, scale)` plays a pattern on one target for the lab regardless of the strength, lane, route, cooldown and budget (not while hidden; it shows in `report()` as `audition`), `cues()` and `tuning()` return copies of the cues and of the compiler constants and budget as tuned, `tune({ rumble })` changes the rumble compiler (`tapBase`, `tapSpan`, `slice`, `merge`, `floor`, `maxSegments`, `maxMs`, checked against `RUMBLE_LIMITS`) through `tuneRumble` on the gamepad backend, `preview(id, target)` plays a cue at once on one target at that target's strength, for a settings screen (it ignores the lane, cooldown, route and budget, but not Off or a hidden page), `setGameplay` closes the game lane outside a level, `setActive(false)` stops everything while the page is hidden, `tune(patch)` changes cues, compiler constants and the budget (range-checked, returning `{ applied, refused }`), and `report()` lists the last plays with their compiled arrays and why cues were dropped. The table is copied on construction, so tuning never changes the module's table.
- Presentation only: nothing here reads or feeds back into the sim. An episode supplies the cue table (Episode 1: `episodes/episode-1/src/haptics/fizz-haptics.ts`). `haptic-strength.ts` holds the four strengths a player chooses (Off, Light, Medium, Strong, the master scales 0, 0.5, 0.75 and 1) shared by the phone and the controller; the phone's level is `hapticStrength` in the touch settings and the controller's is the episode's `rumble` option, and `GameHaptics.setScale(device, controller)` takes the two scales. Haptics are on by default where a device can use them; `?haptics` and `?haptics=off` override both strengths for a visit without saving (the episode's `url-lock.ts` parses the flag and renders the fixed rows as "(link)"). **Haptics lab** (`?debug` or Options > Haptics > Haptics lab, `hapticsLab` in `lf-ep1-options-v1`, default off): `ui/haptics-lab.ts` (DOM) over the pure `haptics/lab.ts` (cue groups, compiled results, a timeline, event drafts, slider specs, the backend choice, the status line, the compare and floor-ladder runs, and `hapticTuneDiff`). It reuses the sound lab's `#lab` overlay, styles and host pattern, is imported on demand, and `Game.syncLab` mounts or removes it as the options change. Cues lists a button per cue (Ben, Pickups, World, Boss, Level, Menus, Editor) with its compiled length on the phone and the pad; Tune edits up to six events (tap or hum: start, length, start, peak and end strength, sharpness) and the cue's cooldown, priority and policy, with the pulse array and a bar timeline for each target and Play and Play original; Compare plays the phone then the controller three times 400 ms apart, a cue at 0.5, 0.75 and 1.0, and a floor ladder of taps from 0.1 to 1.0; Compile has sliders for `PERIOD`, `MIN_ON`, `MIN_OFF`, `FLOOR`, `T_BASE`, `T_SPAN`, the pad minimum, tap extra and segment length, and the budget. The header picks the backend (Auto follows the route, Phone, Controller or Off, each disabled with its reason when it cannot play), sets a lab-only strength from 0 to 1.5, copies only what moved as JSON in the `debugHapticsTune` shape (a changed cue is written whole; the clipboard refusing falls back to the console), resets to defaults and shows one status line (phone and pad state, whether the page has had a tap, the last compiled result). Escape closes the lab without pausing. See `docs/MOBILE.md` for the compile rules and what is unverified.

### 6.2 Lifecycle — Fullscreen and lock built (7.1); wake lock and auto-pause built (7.2)
- `lifecycle-policy.ts` (pure): `detectCaps`, `isAppHost`, `resolveFullscreen`, `onGesture` (what a start or resume gesture asks the browser for), `pauseFor` (which page events pause a level in play), `wakeWanted` (live, visible, upright, input within `IDLE_RELEASE_MS`, the setting on, and a wake lock or the app), `isIdle`, `backGuardAllowed`, `fullscreenButton` (whether the explicit Fullscreen button and `F` show on a screen kind, touch or desktop, and which glyph and name; built in 7.6), `lifecyclePolicy` and the `?fullscreen`, `?wake` and `?host` parsers. Window `blur` and an unplugged pad that was in use (`InputManager.onPadLost`) pause a level in play like the other events.
- `lifecycle.ts`: `enterFullscreen(doc, orientation, plan)` makes the `requestFullscreen` call synchronously inside the gesture, locks landscape after it resolves, and never throws; `exitFullscreen(doc)` leaves fullscreen the same way (7.6). `KeepAwakeBackend` (`kind`, `set`, `dispose`, `debug`) has `webWakeLock(nav, doc)` (one request in flight, released when withdrawn before it resolves, asked again on returning to visible, no retry after a refusal until the ask is raised again, never throws) and `noKeepAwake`; the app injects a native backend (app phase). The episode decides which screens are live and which rows are gestures (`lifecycle-rules.ts`). See `docs/MOBILE.md` and `docs/MOBILE_PLAN.md`.
- `keyboard-lock.ts`: `createEscLock({ keyboard, secure })` wraps `navigator.keyboard.lock(['Escape'])` and `unlock()` so Esc still reaches the page in desktop fullscreen. `engage(touch)` asks (skipped on touch or an insecure page, `unsupported` without the API, `denied` on a throw or rejection) and `held` is true only once the browser has agreed; `release()` unlocks, and undoes a lock that arrives after it. The shell engages on `fullscreenchange` into fullscreen and releases on leaving it.
- `fullscreen-backend.ts`: `FullscreenBackend` (`kind`, `isFullscreen`, `enter(plan)`, `exit`, `onChange`, `escapeCaptured`, `dispose`) is how the shell enters, leaves and watches fullscreen. `webFullscreenBackend({ doc, orientation, keyboard, secure, touch })` wraps `enterFullscreen`, `exitFullscreen` and `fullscreenchange` and holds the Esc lock (`escapeCaptured` is true only once the browser granted it); the app can inject another.

## 7. Input
- Keyboard:
  - Keen-style layout: Ctrl jump, Alt pogo, Space fire.
  - Modern layout: Z, X, C.
  - Arrows or WASD move.
- Pause keys: Esc, `P` and the Pause/Break key (`pauseKeyKind` and `isFieldTarget` in `input.ts`; key-down edge only, never while typing in a field). The Esc key's `pause` command carries `esc: true` so the shell can tell it apart.
- Gamepad via the standard mapping: A jump, B/Y pogo, X/RT fire, Start menu.
- **Touch** (`touch.ts`, `touch-layout.ts`, `touch-ui.ts` in the engine): on-screen controls in a level. The pure `TouchState` tracks every finger by pointer id (so moving and jumping work together), a sliding D-pad turns a thumb's offset into directions (with a dead zone and a rule that drops the weaker axis), and a fresh Jump, Pogo or Fizz press is held for at least 50 ms so a tap shorter than one fixed step still reaches the sim. `placeControls` lays the controls out from the window size and the safe-area insets (every hit area at least 48 dp, the glass face inside it); `TouchControls` is the thin DOM layer; it can show a reduced set of controls (a hidden control takes no new touch) and reports `sideGutters`, the room menu content leaves for the controls showing. Touch bits count whenever the controls show, so on menu-style screens they drive the menus as a gamepad does: the shell shows the D-pad where there is something to move, relabels Jump as Select and Pogo as Back, hides Fizz and keeps Pause where it has a job. Choosing and going back need a fresh press, so a button already held when a menu opens chooses nothing until it is pressed again. The shell's touch mode follows the last-used device (touch, keyboard or gamepad); `?touch` pins it on. The player's touch settings live in `touch-settings.ts` (key `lf-touch-v1`: Size, Opacity, Left-handed, haptic strength and moved controls, parsed with per-field defaults; an older `haptics: false` reads as strength Off) and become a `TouchSpec` through `touchSpec`. A moved control is an `EdgeOffset` from its own safe corner in `TouchSpec.moved`; `placeControls` clamps it into `controlZone` (its own side, below a 96 px top band, inside the safe area, leaving menus a 300 px column), and if the result is not a `validPlacement` (hit areas inside the safe area and apart, faces 8 px apart) it falls back to the default places for the whole layout and reports `PlacedControls.custom`. `dragControl` and `offsetOf` turn a finger position into a legal place and its offset, `dragOffset` rounds that to the whole spec pixels that are saved and checks them by placing the controls, and `TouchControls.setSpec` applies a changed spec while running. `TouchControls.setEditing(on, { pick?, drop })` is the edit mode: touch input is off, a finger picks up one of the four movable controls (never Pause) with the grab offset kept so it does not jump, the control follows it through `dragOffset`, and `drop(id, offset)` reports the final place when the finger lifts, is cancelled, or the placement changes under it; the episode saves the offset. The controls are named "Move …" in the editor.
- **Browser Back** (`back-guard.ts` in the engine): `BackGuard(onBack, history, target)` holds one history entry (`pushState({ lfBack: 1 })`, same URL) while the game wants Back, however many screens open, and exposes `set(want)`, `armed` and `dispose()`. `set(false)` calls `history.back()` and counts the `popstate` it causes so it is swallowed; wants made while removals are landing are deferred, and the latest wins. A user Back disarms the guard and calls `onBack`, then re-arms if the want stands. A page that opens on a leftover entry clears it with `replaceState(null, '')`. The shell decides when to want it (fullscreen, an installed app, or `?back`) and what Back does on each screen.
- **Menu repeat** (`repeat.ts` in the engine): a held direction fires on the press, again after 350 ms and then every 90 ms. `HeldRepeat` works on input bits, so keys, the gamepad and the touch D-pad repeat alike, fires at most once per frame, and makes a direction held across a screen change wait for a release.
- **Rumble pad:** `InputManager.activePad()` returns the gamepad that last had input (or the first connected one, or null) for the rumble backend; `pickPad` is the pure choice.
- Edge detection happens per fixed tick.
- **Planned:** in the Tauri shell, capture Ctrl/Alt so they don't trigger browser shortcuts.
